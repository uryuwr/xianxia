# 玩法系统 · 方法论

## 搜打撤循环（extraction loop）
- 核心张力 = 带回的价值 × 失去的风险。三根杠杆：时间压力（天时 → 入夜妖潮）、负重（储物袋占格）、身陨损失（按区域保留比例 + 遗落储物袋可取回）。
- 每局都要有"带回一点"的保底，否则新手连续空手会流失：区域一身陨保留一半、遗落储物袋下一局可取回。
- 出发前决策（带什么丹药、装什么功法）与局内决策（继续搜还是撤）分开呈现：出行准备给信息（本去处护盾、克制），局内只给结果。

## 教学：做中学，记录事实而非弹窗
- 每个教学点 = 一个可观察的事实（拾取、破盾、服丹）。玩家已经做到的就不再教；顺序允许乱。
- 守关敌人要"守"：明确的场地边界 + 有限的仇恨与脱战距离，玩家能选择何时挑战。

## 场景流程（状态机）
- 每个场景一个对象：`enter(data)` / `exit()` / `update(dt)`，`flow.go(name, data)` 切换；全局只有一个 Esc 链。
- 场景之间只传数据（region、result），不共享 DOM。

## 存档
- 新字段一律给缺省值，读档时迁移（`migrateBuild`：旧档首次读入时按 learned 填一次，打 `buildV2` 标记）。
- 局内状态不写进 profile，结算时一次性写；中途关闭页面按身陨结算（首次豁免）。

## 可测试性
- 每个规则至少一条可运行断言，用真实按键（keyboard.press）测输入链路，用 `c.ev` 读内部状态。
- 偶发失败要找根因（时序、免伤窗口），用"等状态"代替"等时间"。
- 截图只作人工复核，不作断言。

## 委托与奇遇（模块 E）
- **可复现的随机**：委托与奇遇都用 `mulberry32(hash(存档创建时间, 槽位, 局号 / 种子))`，同一存档同一局号的委托固定（退出重进不会刷新），测试可复现。不同用途用不同的 hash 前缀（"offers" / "encroll" / "enc" / "quest" / "reward"），避免一处多抽一次就改变另一处。
- **"不会全是同一类"**：模板分组（combat / gather / route），先打乱组再每组按权重抽一个，不够再从剩余模板补——保证至少两类，比"抽完检查、不行重抽"稳定。
- **按权重不放回抽取**：每抽一个就从候选里删掉，同局不重复。
- **单独掷 vs 占名额**：高频小惊喜（灵田）单独按概率掷，不挤掉剧情奇遇的名额；剧情奇遇按 0–2 个的分布抽。期望值用 2000 个种子统计验证（见 loop_quests）。

## 洞府（模块 C）

### 据点（局间）
- 局间要短：据点只做"为下一局准备"的事，站点越少越好；每个要玩家决定的事都应能从一个总览（今日可办）一键直达。依据：玩法评审 G5 引用的怪物猎人据点分析。本项目：8 个站点并为 4 个 + 天机镜台。
- 据点即界面：设施就是场景里的建筑，信息挂在建筑上但默认隐藏（悬停 / 靠近才出现）。
- 反馈不可错过：系统替玩家做的事必须有持久反馈（待办、场景状态），不能只靠一闪而过的 toast。
- 制作小游戏化：炼丹是"按住加火、松开降温、追游走的火候带"的一维控制，评分只看在带内的时间比例；熟练后可跳过。
- 大加载：静态遮罩下分帧构建 → 并行编译（KHR_parallel_shader_compile）→ 分帧上传 → 首绘 → 揭开，单帧 ≤ 50ms。

## 构筑与成长（系统框架，2026-11-18，构筑与成长 v1 · 01）
- **轴收敛**：成长轴按"一种资源 ↔ 一个站点 ↔ 一个动词"收成三条：境界（修为 → 灵泉）、功法（悟性 → 参悟 / 加重）、法器（材料 → 炼器 / 祭炼），外加"装备 + 局内拾取"一层赌注。新增成长先问"能不能挂到已有轴上"，不能才加；**计量单位尽量共用**（本项目：法术 / 阵法 / 法宝都用"几重"）。依据：Sid Meier GDC 2012"有趣的决定"（《文明》删第二棵科技树）。
- **概念预算表**：每个新增给玩家的概念写一行（首次出现在第几局、是不是新词、复用了什么），合计新词数，并对照玩法评审 P2 的"前 3 局概念数"不增加；同时列"明确不做的"清单。
- **投入越深越安全**（搜打撤 × 构筑）：局外精进（重、祭炼、已学功法）永不丢；装备与本局拾取是赌注层；首杀 / 选择点奖励进护身格。Hunt: Showdown 的"会死的猎人 + 永久血脉"两层同理。
- **三选一选的是先后，不是有无**：没选的件放进后续来源（重探 / 重战 / 夜明宝箱），既消除"选错"焦虑，又给之后的出行一个目标。
- **多来源、顺序无关的选择匣**：同一类大选择（如本命法宝）给 2–3 个来源（境界保底 / 首领 / 遗府），**谁先打开谁是三选一**，第二个二选一，第三个直接给——非线性路线（首领不是硬门）下栏位不空、来源不浪费。
- **偏置跟着装配走**：掉落偏置按出发时身上的流派标签现算，不立"道途"存档值——换装即换偏置，不需要改选界面（D3 Smart Loot 偏置不保证 + Hades 镜子随时切换）。
- **改选代价阶梯**：装配 / 已解锁变体免费换 → 精进投入"散功"按比例返还（小代价，Hades 退暗晶要 1 把钥匙）→ 大境界（筑基）一次全额重修。
- **先算节奏，再定来源是随机还是确定**（构筑与成长 v1 的教训）：先用经济模拟得出"练 X 层 ≈ 第几局"（本项目：一次回府约升两层，练 X ≈ 第 (X+1)/2+1 局，区域一只有 2–3 局），再按"筑基前剩几局 × 每局概率"判断一个部件能不能靠随机掉落拿到（剩 4 局要每局 ≥ 25% 才有约 68%）。拿不到的**流派核心件一律走确定来源**（选择、赠予、匣），随机掉落只负责增强件。主管草图用"必 1 / 常 0.6 / 罕 0.25"粗估，比真实掉率乐观 1–2 个境界。
- **偏置要用替换式，不用加权式**：掉落池按地图分区预先收窄时，"同流派权重 ×2"在分区外只剩约 11%；替换式（命中心法时以概率 b 换成本流派未有的一本）才稳定，并与分区偏置相乘后设总封顶（本项目 b = 0.5、封顶 75%，数值 03 §6）。
- **汇总多岗位方案的做法**：先发框架草案（轴、选择点、栏位）给各岗位 → 收到回复当轮就改自己的稿并回消息"采纳 / 改口径"→ 分歧表写"各方立场 + 我的建议 + 状态（已定 / 用户题 / 后续）"，三方一致的不再出用户题；用户题合并去重到 ≤ 6，每题带推荐和出处。
